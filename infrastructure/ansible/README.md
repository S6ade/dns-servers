# Ansible: Автоматизация настройки DNS-серверов

Этот раздел проекта отвечает за **конфигурацию** виртуальных машин, созданных в Terraform. Здесь мы превращаем «чистые» серверы Ubuntu в работающие DNS-серверы: авторитетный (Bind9) и кэширующий (Unbound).

## 📖 Зачем это нужно

Terraform создает инфраструктуру (виртуальные машины, сети, диски). Но когда машина загружается, она представляет собой чистую операционную систему. **Ansible** позволяет автоматизировать рутину:

* Установку пакетов (`apt install`).
* Копирование конфигурационных файлов (шаблоны с переменными).
* Настройку файрвола (UFW).
* Управление службами (запуск, перезапуск, автозагрузка).

Вместо того чтобы заходить на каждый сервер по SSH и вручную вводить десятки команд, мы запускаем один плейбук, и Ansible делает всё сам.

## 🏗️ Архитектура и роли

Проект построен на **ролях (roles)**. Роль — это переиспользуемый набор задач, шаблонов и переменных для конкретного сервиса.

```text
ansible/
├── inventory.ini             # Где находятся серверы (не в Git)
├── inventory.example.ini     # Шаблон для настройки
├── playbooks/
│   ├── bind9.yml             # Плейбук для Bind9 (точка входа)
│   └── unbound.yml           # Плейбук для Unbound
└── roles/
    ├── bind9/
    │   ├── defaults/         # Переменные (домен, IP)
    │   ├── handlers/         # Перезапуск при изменении
    │   ├── tasks/            # Что делать (установка, копирование)
    │   └── templates/        # Шаблоны конфигов (зоны, named.conf)
    └── unbound/
        ├── defaults/
        ├── handlers/
        ├── tasks/
        └── templates/
```

### Роль Bind9 (Авторитетный DNS)
* **Что делает:** Устанавливает Bind9, создает прямую и обратную зоны, настраивает резолв имен в IP (и обратно).
* **Ключевые файлы:** `db.zone.j2` (прямая зона), `db.10.j2` (обратная зона), `named.conf.local.j2` (конфиг зон).
* **Результат:** Сервер отвечает на запросы `www.<домен>` и умеет делать обратный резолв.

### Роль Unbound (Кэширующий DNS)
* **Что делает:** Устанавливает Unbound, отключает системный `systemd-resolved` (чтобы освободить порт 53), настраивает кэш и права доступа.
* **Ключевые файлы:** `main.conf.j2` (конфиг кэша, интерфейсов и access-control).
* **Результат:** Сервер кэширует ответы от внешних DNS. Первый запрос долгий, повторный — мгновенный (из кэша).

## ⚙️ Требования

Перед запуском убедитесь, что у вас установлены:
* Ansible (версия 2.9+).
* SSH-ключ (тот же, что использовался в Terraform для доступа к VM).

## 🚀 Быстрый старт

### 1. Настройка Inventory
Скопируйте шаблон и заполните его реальными IP-адресами ваших серверов (их выдает Terraform):

```bash
cp inventory.example.ini inventory.ini
nano inventory.ini
```

Внутри должно быть указано:
* Группа `[dns_bind]` — IP вашей bind-vm.
* Группа `[dns_unbound]` — IP вашей unbound-vm.
* Путь к приватному SSH-ключу.

### 2. Проверка связи
Убедитесь, что Ansible видит серверы и может к ним подключиться:

```bash
ansible all -i inventory.ini -m ping
```
*(Вы должны увидеть зеленые сообщения `SUCCESS => {"ping": "pong"}`).*

### 3. Запуск настройки Bind9
```bash
ansible-playbook -i inventory.ini playbooks/bind9.yml
```
После завершения на bind-vm будет установлен и настроен авторитетный DNS-сервер.

### 4. Запуск настройки Unbound
```bash
ansible-playbook -i inventory.ini playbooks/unbound.yml
```
После завершения на unbound-vm будет установлен кэширующий DNS-сервер.

## 🧠 Как это работает (на примере Bind9)

Плейбук `playbooks/bind9.yml` говорит: «Примени роль bind9 к группе dns_bind». Ansible идет в папку `roles/bind9/` и читает `tasks/main.yml`. Задачи выполняются по порядку:
1. Установка пакетов (`bind9`, `bind9utils`, `dnsutils`).
2. Копирование шаблона `named.conf.local.j2` на сервер. (Внутри шаблона переменные `{{ bind_domain }}` заменяются на реальные значения из `defaults/main.yml`).
3. Копирование файлов зон `db.zone.j2` и `db.10.j2`.
4. Запуск службы `bind9`.

Если конфиг изменился, срабатывает handler (`restart bind9`), и служба перезапускается, подхватывая новые настройки.

# 📊 Инструкция по проверке результатов настройки DNS

В данном руководстве приведены команды для проверки корректности работы авторитативного DNS-сервера **Bind9** и кэширующего резонатора **Unbound**.

---

## 🌐 1. Тестирование Bind9 (на хосте `bind-vm`)

### **Шаг 1. Валидация конфигурации**
Проверка синтаксиса основных конфигурационных файлов:
```bash
sudo named-checkconf
```
* **Ожидаемый результат:** Команда завершается без вывода. Это означает, что конфигурация не содержит синтаксических ошибок.

### **Шаг 2. Проверка зоны прямого просмотра**
Проверка файла зоны `s6ade.local`:
```bash
sudo named-checkzone s6ade.local /etc/bind/db.s6ade.local
```
* **Ожидаемый результат:**
  ```text
  zone s6ade.local/IN: loaded serial 2026102201
  OK
  ```

### **Шаг 3. Проверка зоны обратного просмотра**
Проверка корректности файла обратной зоны для подсети `10.0.0.0/24`:
```bash
sudo named-checkzone 0.0.10.in-addr.arpa /etc/bind/db.10
```
* **Ожидаемый результат:**
  ```text
  zone 0.0.10.in-addr.arpa/IN: loaded serial 2026102201
  OK
  ```

### **Шаг 4. Тестирование прямого разрешения (A-запись)**
Запрос IP-адреса для доменного имени:
```bash
dig @localhost www.s6ade.local
```
* **Ожидаемый результат** (обратите внимание на секцию `ANSWER SECTION`):
  ```text
  ;; ANSWER SECTION:
  www.s6ade.local.  36000  IN  A  <IP_вашего_клиента>
  ```

### **Шаг 5. Тестирование обратного разрешения (PTR-запись)**
Запрос доменного имени по IP-адресу:
```bash
dig @localhost -x 10.0.0.10
```
* **Ожидаемый результат** (в секции `ANSWER SECTION`):
  ```text
  ;; ANSWER SECTION:
  10.0.0.10.in-addr.arpa.  36000  IN  PTR  ns1.s6ade.local.
  ```

---

## 🏎️ 2. Тестирование Unbound (на хосте `unbound-vm`)

### **Шаг 1. Контроль сетевых портов**
Убедитесь, что стандартный DNS-порт (53) занят именно процессом Unbound:
```bash
sudo ss -tulpn | grep :53
```
* **Ожидаемый результат:** Порт `53` слушает исключительно `unbound`.
* *⚠️ Внимание:* Если порт занят службами `systemd-resolve` или `named`, их необходимо отключить во избежание конфликтов.

### **Шаг 2. Холодный запрос (проверка разрешения внешних имен)**
Выполните первичный запрос к внешнему ресурсу:
```bash
dig @localhost practicum.yandex.ru
```
* **Ожидаемый результат:**
  * Статус ответа: `status: NOERROR`.
  * Время выполнения (`Query time`): **от 50 до 200 мс** (сервер запрашивает данные из внешней сети).

### **Шаг 3. Горячий запрос (проверка работы кэша)**
Повторите тот же запрос для проверки кэширования:
```bash
dig @localhost practicum.yandex.ru
```
* **Ожидаемый результат:**
  * Время выполнения (`Query time`): **0 msec** (или близко к нулю). Это подтверждает, что ответ успешно извлечен из локального кэша Unbound.


## ⚠️ Troubleshooting (Типичные проблемы)

* **Failed to update apt cache after 5 retries**
  * *Причина:* Сервер только что создан, и cloud-init еще занимает apt, либо сеть нестабильна.
  * *Решение:* Подождите 2-3 минуты и запустите плейбук снова. Или добавьте `lock_timeout: 300` в задачу apt.

* **Unit unbound.service could not be found**
  * *Причина:* Пакет не установился (Ansible упал на предыдущем шаге).
  * *Решение:* Проверьте вывод плейбука, найдите ошибку и исправьте её.

* **Порт 53 занят systemd-resolved**
  * *Причина:* Системный резолвер перехватывает порт.
  * *Решение:* В роли unbound мы отключаем его через `DNSStubListener=no`. Если не сработало — остановите его вручную: `sudo systemctl stop systemd-resolved`.

* **named (Bind9) занимает порт 53 на unbound-vm**
  * *Причина:* Случайно установили Bind9 на машину, где должен быть Unbound.
  * *Решение:* Остановите его: `sudo systemctl stop named && sudo systemctl disable named`.
